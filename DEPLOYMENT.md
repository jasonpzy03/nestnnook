# Deploying Nest & Nook to Vercel

Use three Vercel projects connected to the same repository. Test a separate branch before updating the existing live client. Local configuration files are not uploaded: set production environment variables in Vercel.

| Project              | Root directory                   | Configuration                          |
| -------------------- | -------------------------------- | -------------------------------------- |
| Existing public site | Repository root                  | Root vercel.json; DEPLOY_TARGET=client |
| New admin            | Repository root (not apps/admin) | Root vercel.json; DEPLOY_TARGET=admin  |
| New API              | apps/api                         | NestJS preset; apps/api/vercel.json    |

Use Node.js 22.x. For root projects, use the Other framework preset, `npm ci` install, `npm run build:vercel` build and `.vercel/output` output. Remove old dashboard overrides that still point to `dist`. The Build Output API contains the static assets, routes and SSR function.

## 1. Create the admin project

Import the repository again. Set `DEPLOY_TARGET=admin` and initially `API_ORIGIN=https://api.example.com` as a temporary placeholder. Deploy to obtain the actual stable admin URL. Login will work only after the API is deployed and the placeholder is replaced. The admin's static package includes a same-origin `/api/*` proxy; local proxy.conf.json is not used in production.

## 2. Create the API project

Import the same repository, select root `apps/api` and the NestJS framework preset. Keep automatic framework build/output defaults and use `npm ci` for installation. Set these private environment variables:

```dotenv
NODE_ENV=production
STORAGE_DRIVER=upstash
UPSTASH_REDIS_REST_URL=your-rest-url
UPSTASH_REDIS_REST_TOKEN=your-rest-token
REDIS_KEY_PREFIX=nestnnook-prod
ADMIN_ORIGIN=https://YOUR-ACTUAL-ADMIN-DOMAIN
ADMIN_PASSWORD_HASH=your-scrypt-hash
ALLOW_LOCAL_UPLOADS=false
```

ADMIN_ORIGIN must match the admin origin exactly, with no trailing slash. The hash format is the existing salt:hash generated by local setup, not the plaintext password. You can retain your current login by copying ADMIN_PASSWORD_HASH privately from apps/api/.env. Do not commit credentials.

Use a separate database or prefix for production. A new prefix initialises the original seed catalogue; local draft edits are not migrated. Reusing both the existing database and prefix uses the exact same catalogue and auth namespace, so local publishing also changes production content. Seed JSON is a literal module dependency so the NestJS bundler can include it without a custom functions pattern.

Open `https://YOUR-API-DOMAIN/api/public/catalog`; it should return JSON (empty rooms and locations until individually published). The production endpoint must be reachable by the client SSR function and admin proxy without a Vercel platform login. Admin management endpoints remain protected by the application's session guard.

## 3. Connect the admin

Replace its API_ORIGIN with `https://YOUR-API-DOMAIN` (no `/api` suffix) and redeploy. Sign in, publish locations, then publish rooms. When assigning rooms, their location must already be published. Use the stable admin domain matching ADMIN_ORIGIN, not a deployment-specific preview URL.

Original `/assets/` photos ship with both frontend builds. `/uploads/` files on your computer do not: replace local upload references with hosted HTTPS image URLs before publishing production rooms. Production image uploads are not yet configured.

## 4. Update the existing public project

Keep the existing Vercel project and domain. Use root settings from the table above and add:

```dotenv
DEPLOY_TARGET=client
CATALOG_API_URL=https://YOUR-API-DOMAIN/api/public/catalog
```

Set the variables for each deployment environment you intend to use. Deploy the tested code version after the API is ready. The existing seo.config.json keeps the public canonical domain. Redis credentials belong only in the API project.

## 5. Verify

Check admin login, original images, public HTML containing room names/prices, robots.txt and sitemap.xml. Save a room draft: the public page must remain unchanged. Publish that room and refresh the public page: the new data must appear without deploying. Unpublish and confirm removal. Check Vercel runtime logs for any 503s. Existing open browser tabs need a refresh to see publication changes.

No deploy hooks are used for content changes. Code changes still require deployments. Vercel deployment and API proxy behaviour must be verified on the actual hosted URLs; local package builds do not verify cloud routing.
